# Linux memory for the x86_64 XNU bootstrap

The bootstrap needs one physically contiguous interval owned by Linux for the full lifetime of the XNU instance. The allocator supplies the physical base, length, and a private release handle to the x86 loader. Its inputs are the size and placement constraints from the selected artifact. An address supplied by an operator, an EFI RAM descriptor, and a PFN that happens to be online cannot establish exclusive ownership.

## Placement

Size the interval for the boot argument page, EFI map, ADT, rounded kernel image, and artifact-specific bootstrap budget. The metadata precedes the image. Check the complete interval for overflow and keep it below 4 GiB. With 4 KiB pages, the greatest page-aligned XNU allocation cursor is `0xfffff000` because `ID_MAP_VTOP` drops the high bits. This cursor limit applies to the consumed bootstrap span, including the randomized physmap and `__HIB` double-map budget. [Source-pinned layout #189](https://github.com/Personed/liXNU/pull/189) · [Table budget #193](https://github.com/Personed/liXNU/pull/193)

The first page-table activation has a tighter bound. `fillkpt` populates one 4 KiB mapping per page from physical address zero, so the rounded image end plus the fixed tables must fit within `NKPT × 512 × 4096` bytes. The default `NKPT=500` gives a 1000 MiB aperture ending at `0x3e800000`. Require the effective `NKPT` from the selected build, including any override, before accepting a layout. A DMA32 allocation can satisfy the 32-bit address limit and still start above the aperture. Pass the actual allocated base to the pinned layout validator before populating or exposing the region. [Pinned `NKPT`](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/i386/pmap.h#L223-L232) · [Pinned page-table setup](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/i386/i386_init.c#L385-L425)

## Allocation paths

These are header-package observations. Check the actual build tree's `Module.symvers` and config with Kbuild before selecting a path.

| Linux headers inspected | Contiguous allocation available to modules |
| --- | --- |
| Ubuntu 24.04 HWE `7.0.0-44-generic`, package `7.0.0-44.44~24.04.1` | `CONFIG_CONTIG_ALLOC` and `CONFIG_ZONE_DMA32` enabled. Exports `alloc_contig_pages_noprof` and `free_contig_range`. |
| Debian 13 `6.12.118+deb13-amd64`, package `6.12.118-1` | Both configs enabled. Exports the exact-PFN `alloc_contig_range_noprof` and `free_contig_range`. The page-search wrapper `alloc_contig_pages_noprof` and memory hotplug read-lock helpers are absent from `Module.symvers`. |

**Runtime allocation.** Where Kbuild can link the page-search wrapper, use `alloc_contig_pages` with `GFP_KERNEL | GFP_DMA32 | __GFP_NOWARN` in sleepable Linux context, without `__GFP_COMP`. Bound and round the request before converting bytes to a page count. A power-of-two page count provides an alignment guarantee on the inspected kernel and may consume extra memory. The wrapper searches eligible zones and returns referenced pages. Keep the first page and actual page count, derive the base with `page_to_phys`, and validate the result. Reject an unsuitable placement and immediately return the entire range with `free_contig_range(page_to_pfn(first), nr_pages)`. Avoid retrying the same unbounded search to find a smaller physical address. For small synthetic tests, `alloc_pages_exact` with `GFP_DMA32` and `free_pages_exact` are available on both profiles. The buddy order limit restricts that pair to small extents. [Linux 7.0 page allocator](https://github.com/torvalds/linux/blob/v7.0/mm/page_alloc.c#L7222-L7376) · [Linux 6.12 page allocator](https://github.com/torvalds/linux/blob/v6.12/mm/page_alloc.c#L6655-L6770)

**Bounded early reservation.** For a larger extent on kernels without the module wrapper, the proposed fallback is an explicit built-in x86 Linux provider. It selects a supported profile with a fixed size, alignment, and physical ceiling, then calls `memblock_phys_alloc_range` during x86 boot after discovering RAM and reserving early firmware and kernel ranges, before memblock hands its free pages to the buddy allocator. Use a ceiling at or below the smallest `NKPT` aperture accepted by the profile, with the consumed extent kept within the cursor limit. Keeping the entire reservation inside that bound is a conservative placement policy. The provider checks that the returned base is nonzero, the interval is contained within the configured bounds, and memblock marks it reserved. At runtime the provider grants one exclusive, opaque lease at a time for that boot's range. The loader validates the leased address and size against the current artifact again. The module returns the lease after cleaning up its mappings, and the pages stay reserved until reboot. Rebuild and boot the host kernel to validate this provider before relying on it for Debian. [Linux 6.12 memblock allocation](https://github.com/torvalds/linux/blob/v6.12/mm/memblock.c#L1510-L1542)

The generic `reserve_mem=size:align:label` option is present in both packages with a GPL-exported `reserve_mem_find_by_name`. Its syntax has no maximum address and its lookup does not acquire an exclusive lease. Prefer the bounded provider for the x86 bootstrap. An exact-PFN scan by an out-of-tree module would need to stabilize page and zone lifetimes during hotplug, check the exact allocator's migratetype and single-zone preconditions, and own the resulting allocation. The exported Debian exact-PFN call alone is insufficient for that scan. [Linux 6.12 named reservations](https://github.com/torvalds/linux/blob/v6.12/mm/memblock.c#L2255-L2365) · [Linux 6.12 exact-PFN allocator](https://github.com/torvalds/linux/blob/v6.12/mm/page_alloc.c#L6513-L6550)

**CMA and DMA.** Debian's inspected config has CMA disabled. Ubuntu enables CMA and DMA CMA, but neither profile exports `cma_alloc`/`cma_release` or `dma_alloc_from_contiguous`/`dma_release_from_contiguous`. A CMA area would need a verified physical limit and its allocator to claim and release the bitmap entry. A device DMA mask constrains device addresses. With an IOMMU a DMA handle can be an IOVA, and a contiguous DMA mapping can represent separate physical pages. Obtain CPU physical addresses from owned pages instead of treating `dma_addr_t` as a PFN. [Linux DMA address spaces](https://github.com/torvalds/linux/blob/v7.0/Documentation/core-api/dma-api-howto.rst#cpu-and-dma-addresses) · [Linux coherent DMA mapping](https://github.com/torvalds/linux/blob/v6.12/kernel/dma/mapping.c#L590-L632)

## Ownership and validation

1. Acquire pages or the boot provider's exclusive lease before any initialization writes. Validate the returned extent and acquire only a writable, non-executable Linux mapping for preparation. Zero pages within the owned range. Keep the provider kind, original base/count, and release handle private to the host. Treat encrypted-memory address handling as a separate requirement for AMD hosts.
2. If validation or initialization fails before entry, undo mappings and release the full allocation or return the lease. Keep references through entry, faults, return, and shutdown. On shutdown, quiesce XNU and host callbacks, remove aliases and foreign page tables, complete required TLB invalidation, and then return memory. If quiescence or translation cleanup cannot be established, retain the allocation and prevent unloading its owner.
3. Advertise only owned memory as available to XNU. Page-table isolation remains an entry prerequisite because the pinned early identity map begins at physical address zero. Keep the initial profile to fixed-memory hosts until hotplug interactions have been validated.
4. Start with non-executing VM probes on both header profiles. Check alignment, physical bounds and distinct patterns on first and last pages of the owned span. Inject too-large requests and placements inside DMA32 but above the `NKPT` aperture. After each refusal or initialization failure, run another successful allocation to exercise cleanup. Record requested and actual sizes, kernel/package, `NKPT`, allocation path, outcome, and shutdown. A small allocation or a `Module.symvers` check proves only that profile's tested path. Larger requests, boot leases, and physical Intel and AMD execution need their own evidence.
